# SupportFlow API

Backend REST API for **SupportFlow**, a fictional customer support management platform.

This is the **initial release**. It contains only the **Ticket Management** core: create, list, retrieve, update, change status/priority and soft-delete support tickets. Everything else (authentication, users, comments, SLA, notifications, etc.) is intentionally out of scope and reserved for future development.

> All data in this project (seed data, credentials, examples) is **fictional** and exists for development purposes only.

## Architecture

A modular NestJS application with a strict separation of responsibilities:

- **Controller** (`tickets.controller.ts`): HTTP only. Routing, parameter parsing (UUID pipe), DTO binding and Swagger metadata.
- **Service** (`tickets.service.ts`): business logic, including defaults, soft-delete rules, filtering and pagination.
- **PrismaService** (`database/`): a single, globally injectable database client with lifecycle hooks.
- **Global HTTP pipeline** (`app.setup.ts`), shared by `main.ts` and the e2e tests:
  - global prefix `/api/v1`
  - a `ValidationPipe` with `whitelist`, `forbidNonWhitelisted` and `transform`, so unknown or immutable fields are rejected with 400
  - `AllExceptionsFilter`: a consistent error format, with Prisma errors mapped to HTTP codes and no stack traces or SQL exposed
  - Swagger at `/api/docs`
- **Configuration** (`config/env.validation.ts`): environment variables are validated at startup, and the app fails fast when they are invalid.

### Key design decisions

| Decision | Rationale |
| --- | --- |
| `ticketNumber` generated by PostgreSQL via a sequence + `generate_ticket_number()` column default | `nextval()` is atomic, so concurrent inserts can never get the same number. A `UNIQUE` constraint is a second safety net. The number is padded to 6 digits and never truncated (`TCK-1000000` follows `TCK-999999`). |
| UUID primary key generated by the DB (`gen_random_uuid()`) | No client-side id generation needed; built into PostgreSQL 13+. |
| Soft delete via `deletedAt` | Every query filters `deletedAt IS NULL`. Updates use a single `UPDATE … WHERE id = $1 AND deleted_at IS NULL` statement, so there is no read-then-write race. |
| `DELETE` returns `204 No Content` | Standard for a successful delete with no body. Deleting an already deleted ticket returns `404`. |
| Status/priority changed only via dedicated endpoints | `PATCH /tickets/:id` accepts only `title` and `description`. |
| Stable pagination ordering | Sorted by `createdAt`, then `id` as a tie-breaker. |

### Database schema

```
tickets
├── id             UUID          PK, default gen_random_uuid()
├── ticket_number  VARCHAR(20)   UNIQUE, default generate_ticket_number()  -> TCK-000001
├── title          VARCHAR(200)  NOT NULL
├── description    TEXT          NOT NULL
├── status         TicketStatus  NOT NULL, default OPEN
├── priority       TicketPriority NOT NULL, default MEDIUM
├── created_at     TIMESTAMPTZ   NOT NULL, default now()   (indexed)
├── updated_at     TIMESTAMPTZ   NOT NULL (managed by Prisma @updatedAt)
└── deleted_at     TIMESTAMPTZ   NULL (soft delete)

Indexes: status, priority, created_at, ticket_number (via its UNIQUE constraint)
TicketStatus:   OPEN | IN_PROGRESS | WAITING_CUSTOMER | RESOLVED | CLOSED
TicketPriority: LOW | MEDIUM | HIGH | CRITICAL
```

cp .env.example .env

| Variable | Description | Example value (fictional) |
| --- | --- | --- |
| `NODE_ENV` | `development` \| `production` \| `test` | `development` |
| `PORT` | Port the API listens on inside its container or process | `3000` |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | PostgreSQL container credentials | `exemplo_user` / `exemplo_password_dev` / `supportflow` |
| `POSTGRES_HOST_PORT` | Host port mapped to PostgreSQL | `5436` |
| `API_HOST_PORT` | Host port mapped to the API | `3005` |
| `SEED_DATABASE` | Run the idempotent seed on container start | `true` |
| `DATABASE_URL` | Connection string for **host-side** tools (`localhost`) | `postgresql://…@localhost:5436/supportflow` |
| `TEST_DATABASE_URL` | Database used by e2e tests (must end with `_test`) | `postgresql://…@localhost:5436/supportflow_test` |

Docker Compose has no hardcoded credentials and refuses to start if the `POSTGRES_*` variables are missing. Inside Compose, the API's `DATABASE_URL` is built automatically with the **service hostname `postgres`**, never `localhost`.

## Running with Docker

```bash
# Build and start PostgreSQL + API (migrations and seed run automatically)
docker compose up -d --build

# Status (postgres should be "healthy")
docker compose ps

# Logs
docker compose logs -f api

# Stop (data is kept in the named volume)
docker compose down

# Stop and DELETE all database data
docker compose down -v
```

- API: <http://localhost:3005/api/v1/tickets>
- Swagger: <http://localhost:3005/api/docs>

How the stack is wired:

- `postgres` has a `pg_isready` health check.
- `api` waits for `condition: service_healthy`.
- Both share the `supportflow-api-internal` bridge network.
- Data persists in the `supportflow-api-postgres-data` volume.
- The API image is multi-stage: the build stage compiles TypeScript and prunes dev dependencies, and the runtime stage runs as the non-root `node` user.
- On first initialization of the volume, `docker/postgres/init` creates the extra `supportflow_test` database for e2e tests.

## Database

### Migrations

Migrations are applied automatically when the API container starts (`prisma migrate deploy`). To run them manually:

```bash
# inside the container
docker compose exec api ./node_modules/.bin/prisma migrate deploy

# from the host (uses DATABASE_URL from .env)
npm run prisma:migrate:deploy

# create a new migration during development
npm run prisma:migrate:dev -- --name <migration_name>
```

The initial migration (`prisma/migrations/20261117000000_init_tickets`) contains hand-written SQL for the ticket-number sequence and function. Prisma's model is kept in sync with it (`prisma migrate diff` reports no drift).

### Seed

The seed creates five fictional tickets (`Exemplo 1` … `Exemplo 5`) with fixed UUIDs. Running it again skips existing tickets, so it **never creates duplicates** and doesn't consume ticket numbers.

```bash
# inside the container (compiled seed)
docker compose exec api node dist/prisma/seed.js

# from the host (TypeScript via tsx)
npm run db:seed
```

When `SEED_DATABASE=true`, the seed runs automatically on every container start.

## API endpoints

Base path: `/api/v1`

| Method | Path | Description | Success |
| --- | --- | --- | --- |
| `POST` | `/tickets` | Create a ticket | `201` |
| `GET` | `/tickets` | List tickets (paginated, filterable) | `200` |
| `GET` | `/tickets/:id` | Retrieve a ticket by UUID | `200` |
| `PATCH` | `/tickets/:id` | Update `title` and/or `description` | `200` |
| `PATCH` | `/tickets/:id/status` | Change status | `200` |
| `PATCH` | `/tickets/:id/priority` | Change priority | `200` |
| `DELETE` | `/tickets/:id` | Soft-delete a ticket | `204` |

Error codes:

- `400`: validation error, invalid UUID, malformed JSON, or a forbidden or unknown field
- `404`: the ticket doesn't exist or was soft-deleted
- `500`: unexpected error (generic message, details only in server logs)

### List query parameters

| Param | Type | Default | Notes |
| --- | --- | --- | --- |
| `page` | integer ≥ 1 | `1` | |
| `limit` | integer 1–100 | `10` | |
| `status` | `TicketStatus` | – | exact match |
| `priority` | `TicketPriority` | – | exact match |
| `search` | string ≤ 200 | – | case-insensitive partial match on `title` |
| `order` | `asc` \| `desc` | `desc` | sort by `createdAt` |

### Examples

```bash
curl -X POST http://localhost:3005/api/v1/tickets \
  -H 'Content-Type: application/json' \
  -d '{"title":"Exemplo 1","description":"Descrição fictícia do chamado Exemplo 1.","priority":"MEDIUM"}'

curl 'http://localhost:3005/api/v1/tickets?page=1&limit=10&status=OPEN&priority=HIGH&order=asc'

curl -X PATCH http://localhost:3005/api/v1/tickets/<id>/status \
  -H 'Content-Type: application/json' -d '{"status":"IN_PROGRESS"}'

curl -X DELETE http://localhost:3005/api/v1/tickets/<id>
```

## Testing

```bash
# Unit tests (no database needed; Prisma is mocked)
npm test

# Integration / e2e tests (Supertest + real PostgreSQL)
docker compose up -d postgres
npm run test:e2e

# Both
npm run test:all

# Coverage (unit)
npm run test:cov
```

The e2e suite:

- uses `TEST_DATABASE_URL`, and refuses to run unless the database name ends with `_test`
- applies migrations automatically
- truncates the `tickets` table before each test

It doesn't depend on any external service or production data.

Covered scenarios:

- **Creation:** creation with defaults; missing or empty title and description; invalid priority; immutable fields rejected.
- **Ticket numbers:** **concurrent creation (30 parallel requests) produces unique, gapless ticket numbers**; uniqueness is enforced by the DB constraint.
- **Listing:** default listing; pagination; status, priority and combined filters; title search; sort order; invalid pagination and filter params.
- **Retrieval:** retrieval; invalid UUID (400); not found (404).
- **Updates:** title/description update, partial update, forbidden fields, empty body; status and priority updates and their validation.
- **Soft delete:** the DB row is kept; deleted tickets are excluded from get, list, search, update and delete.
- **Swagger:** the OpenAPI document is served.

## Known limitations

- No authentication or authorization: every endpoint is public. This is intended for this release.
- No status transition rules: any status can be set from any other status.
- Soft-deleted tickets can't be restored through the API, and there is no hard-delete or purge.
- Ticket-number sequence values consumed by failed inserts (for example, a rolled-back transaction) leave gaps. Uniqueness is always guaranteed; gaplessness is not.
- Search covers `title` only and uses `ILIKE` without a trigram index. That's fine for the current scale, but large datasets would need `pg_trgm` or full-text search.
- Offset pagination; cursor pagination would be better for very large tables.
- The e2e suite needs the PostgreSQL container running.
- The `supportflow_test` database is created only when the PostgreSQL volume is first initialized. On an older volume, create it manually: `docker compose exec postgres createdb -U exemplo_user supportflow_test`.
